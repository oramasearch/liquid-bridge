# Security review of liquid and liquify, October 2026

**For:** https://github.com/oramasearch/liquid-bridge/issues/11, under the open-source release epic
https://github.com/oramasearch/liquid-bridge/issues/16.
**Basis:** liquid `b72fc9f` (`origin/dev`, 2026-10-17) and liquify `dc2a271` (`origin/main`,
2026-10-12; liquify has no `dev` branch yet). Read on 2026-10-21. Every file and line reference is to
those commits.
**Supersedes for status:** [`../publishing/security-review.md`](../publishing/security-review.md),
the September threat model (liquid `a5659bc`, liquify `e7b47ee`). Its trust boundaries (§2) and the
"must never" invariants per component (§3) still hold and are not repeated here; this review
re-checks every one of its findings at today's code, adds the surfaces that did not exist in
September, files one issue per real defect, and scans both histories for secrets.
**Companions:** the pre-public checklist [`pre-public-checklist.md`](pre-public-checklist.md) and the
draft `SECURITY.md` in each repository.

## 1. Summary

- **None of the 27 liquid findings from September has been fixed.** They were never filed as issues;
  the code they cite changed only for features. Three are partly better: tree-sitter grammars are now
  pinned by hash (F11), sync frames cap their decompressed size (F17), and the HTTP client verifies
  the certificate and hostname and never follows redirects (F22).
- **The new code adds the most serious problems.** liquid's signature verifier does not bind a
  signer's name to the key that signed ([L-01](#l-01), Critical): any key verifies as any person whose
  identity chain is not stored locally, which is everyone but the local user. Release approval and
  hot update trust any signer ([L-02](#l-02), [L-06](#l-06)). Package installs and tree
  materialisation can write outside their roots ([L-03](#l-03), [L-04](#l-04)). The HTTP/2 layer
  applies two settings in the wrong direction and has no stream cap ([L-30](#l-30)).
- **liquify's new plugin system loads native code named by the opened repository**, in-process, with
  no prompt ([Y-01](#y-01), High). The AI surface is off by default and keeps its key in the OS
  keychain, but repository text can imitate the user's request and accepted edits are signed as the
  user ([Y-03](#y-03), [Y-04](#y-04)).
- **Secret scan:** gitleaks over every ref of both repositories finds **no real credential**. The only
  key material is the committed self-signed `localhost` TLS fixture already known from September
  ([L-27](#l-27)) and deliberate test vectors (§8).
- **48 issues filed**: 38 in liquid (https://github.com/oramasearch/liquid/issues/383 to
  https://github.com/oramasearch/liquid/issues/420), 10 in liquify
  (https://github.com/oramasearch/liquify/issues/71 to https://github.com/oramasearch/liquify/issues/80).
  11 are `p1`.

### L-01 — verify() accepts any key for any signer name when no identity chain is stored locally

**Critical** · p1 · https://github.com/oramasearch/liquid/issues/383

- `src/identity.cpp:921-925`: when `load_stored_documents(by)` returns `not_found`, `verify` falls back to `verify_with_key(by, ...)`.
- `verify_with_key` (`src/identity.cpp:771-869`) checks the signature against `by.public_key` and compares `signing_key_identifier(by)` with the signature's own field; both come from the same untrusted actor. Nothing binds `by.taap_id` or `by.fingerprint` to `by.public_key` (the fingerprint hashes `created_at` and the label, which the verifier does not have).
- Stored documents exist only for the local signer, so every other person's signature takes the fallback. Callers: `import_synced_drip` / `import_synced_change` (`src/repository/repository_impl.cpp:3145-3190`), `verify_attestation` (`src/attestation/registry.cpp:414`) and through it build-cache results, provenance, hot update and release approvals.
- `by.fingerprint` is also used as a path component in `document_directory` (`src/identity.cpp:448-449`) without an alphabet check.

**Why it matters.** A sync peer or remote sends a drip or change whose author is the victim's `taap_id`, with the attacker's own public key and a valid signature by that key. It is imported as the victim's work. The same forgery satisfies every attestation check, so the signature layer gives integrity but not attribution.

**Fix.** Fail closed when the signer's identity document chain cannot be resolved and verified (require the chain to travel with the signed object, or be pinned), and validate the fingerprint alphabet before using it in a path.

<a id="l-02"></a>

### L-02 — Release approval trusts whatever release policy the repository ships, signed by anyone

**High** · p1 · https://github.com/oramasearch/liquid/issues/384

- `src/identity/threshold.cpp:146-147`: `verify_attestation(policy.statement, ...)` checks only that the policy is validly signed.
- No caller compares `policy.statement.issuer`, or the policy subject, with a trust root. `src/cli/release.cpp:247-255` loads `.liquid/release/policy.cbor` from the repository, and `docs/library/release-approval.md:52` says these files are committed or distributed with the release.

**Why it matters.** Anyone who can write the repository or the release bundle replaces the policy with a self-signed one (threshold 1, signer = themselves), approves the artifact, and `liquid release verify` passes. With L-01, even an honest policy's signers can be impersonated.

**Fix.** Take the policy's signer or digest from a pinned trust root outside the repository and check that the policy subject is the repository being released.

<a id="l-03"></a>

### L-03 — liquid install: package intent symlinks let later intents write and chmod outside the install root

**High** · p1 · https://github.com/oramasearch/liquid/issues/385

- `src/install/install.cpp:410`: `std::filesystem::create_symlink(symlink.target, path, code);` with an absolute host target allowed by `src/install/records.cpp:399`.
- Later intents follow the link: `src/install/install.cpp:353-360` (`make_directories` then `permissions(path, directory.mode, replace)`) and `:382-391` (appends to `staging/etc/passwd` and `group`).

**Why it matters.** A `.deb`, `.rpm` or `.apk` carries an intent that links `etc` to the host `/etc`, and a second that declares `/etc/cron.d` with mode 0777 or adds users. Run as root, `liquid install` changes the host outside the generation.

**Fix.** Create intent symlinks last, resolve every staging path without following symlinks (`openat`/`O_NOFOLLOW` style), and reject intents whose path passes through a symlink.

<a id="l-04"></a>

### L-04 — Tree entry names are never validated, so materialising a tree writes outside its target

**High** · p1 · https://github.com/oramasearch/liquid/issues/386

- `src/vfs/materialise.cpp:85`: `const auto child_target = target / entry.name;`; `src/build/materialise.cpp:53`: `const auto target = destination / entry.name;`.
- Names are accepted unchecked by `decode_tree` (`src/objects/records.cpp:1337-1344`) and by the Git tree parser (`src/git/object_store.cpp:699`).

**Why it matters.** A crafted Git repository (`liquid import git`) or a synced tree with an entry named `..`, `../../.bashrc` or `/etc/x` makes `liquid vfs materialise` or the build materialiser write outside the target; an absolute name replaces the whole path in `operator/`.

**Fix.** Reject names that are empty, `.`, `..`, contain `/`, `\` or NUL, or are case-insensitively `.git`, at tree decode, at Git import, and again at every materialise.

<a id="l-05"></a>

### L-05 — liquid export git writes ref files from unvalidated synced ref names

**Medium** · p2 · https://github.com/oramasearch/liquid/issues/387

- `src/git/export.cpp:175-180`: `name = "refs/heads/" + name;` then `write_text(target / name, ...)`.
- Synced ref names are only checked for being non-empty (`src/repository/repository_impl.cpp:3751-3754`). Tree names are emitted into Git trees unchecked (`src/git/export.cpp:80-84`).

**Why it matters.** A remote serves a ref named `refs/../../../../home/u/.profile`; `liquid export git` creates directories and overwrites that file with a hash. `.git` and `..` names also reach Git consumers.

**Fix.** Validate ref names by Git's `check-ref-format` rules at sync import and again at export, and validate tree names on export (L-04).

<a id="l-06"></a>

### L-06 — Hot update loads a patch signed by any key

**High** · p1 · https://github.com/oramasearch/liquid/issues/388

- `src/hot_update/hot_update.cpp:848-860`: the first attestation that passes `patch_attestation_matches` and `verify_attestation` is accepted; `patch_attestation_matches` (`:317-334`) checks profile and attributes, never `statement.issuer`.
- The patch is a shared library the target process loads (`src/hot_update/runtime.c:148`).

**Why it matters.** Whoever can add a record and a self-signed `hot_update/1` attestation to the repository (sync, a shared checkout) gets their library loaded into the running process: code execution. The signature proves only that someone signed.

**Fix.** Require the issuer to be on a configured allow-list (for example the repository's build identity) before delivering a patch.

<a id="l-07"></a>

### L-07 — Transparency-log verification takes the log's key and witness threshold from the log

**Medium** · p2 · https://github.com/oramasearch/liquid/issues/389

- `src/lake_transparency.cpp:1503-1509` and `:1326-1331`: `identity()` and `configuration()` are fetched from the source on every verify; `witness_threshold` comes from the server (`:1194-1203`); the trusted state stores no log key or witness set (`:786-798`); `http://` is accepted (`:477`).

**Why it matters.** A malicious log, or a network attacker on an `http://` log, returns `witness_threshold: 0` and its own key; witness cosigning then gives no split-view protection on the CLI and repository paths (only the `log_trust` overload avoids this, `docs/library/transparency.md:150-155`).

**Fix.** Pin the log identity and witness policy at bootstrap (in the trusted-checkpoint record or configuration) and refuse a lower server-supplied threshold or a different key.

<a id="l-08"></a>

### L-08 — RFC 4998 renewal chains do not check each link's time against the previous token

**Medium** · p2 · https://github.com/oramasearch/liquid/issues/390

- `src/transparency.cpp:315`: each token is verified at its own `genTime`; `:435-451` never checks that token i+1 was issued while token i's certificate was valid, and never rejects a future `genTime`.

### Y-03 — Repository text can imitate the user-request marker in the AI prompt

**Medium** · p2 · https://github.com/oramasearch/liquify/issues/73

- `src/ai_provider.cpp:38`: `content = request.context + "\n\n[user-request]\n" + request.prompt`; repository-derived source, signatures and diagnostics go into `context` unescaped (`src/context_builder.cpp:115-157`).

**Why it matters.** A comment in a hostile repository containing the marker places attacker text where the user's instruction goes. Edits need Accept and stay in the focus range (`src/assistant.cpp:135-141`), but answers can be steered to mislead.

**Fix.** Send repository context as a separately delimited, escaped data block (or its own content block), and tell the model it is untrusted data.

### Y-04 — Accepted AI edits are signed as the user, with no agent attribution

**Medium** · p2 · https://github.com/oramasearch/liquify/issues/74

- `src/app.cpp:3331-3346`: `apply_edit`, `save_editor`, then a drip signed as the user; the only record is an append to `.liquid/config.liquify.ai.log` (`src/assistant.cpp:184,192-198`).

**Why it matters.** Signed history cannot tell a model's edit from the user's; the side log is unsigned and editable. The AI design requires agent attribution under attenuation-only delegation.

**Fix.** Apply accepted assistant edits through libliquid's agent and structural-edit path so the drip carries an agent attribution and a scoped lease.

### Y-05 — AI can be enabled for every repository at once, and a repository's own settings can enable it

**Low** · p3 · https://github.com/oramasearch/liquify/issues/75

- Settings merge user then repository (`src/settings.cpp:572-575`); with no repository open the checkbox writes user scope (`src/app.cpp:1411-1412,2311-2317,4870-4872`); `.liquid/settings.liquid` can set `ai { enabled: true }` (`src/settings.cpp:273-275`).

**Why it matters.** The design asks for a per-repository switch, default off, because one repository under NDA is enough. Nothing is sent until the user invokes an action.

**Fix.** Ignore `ai.enabled` from user scope and from repository-shipped files; keep the opt-in in per-user state keyed by repository identity.

### Y-06 — Saving repository-scope settings copies the user's merged settings, including Lake accounts, into the repository

**Low** · p3 · https://github.com/oramasearch/liquify/issues/76

- `src/app.cpp:2313-2317` saves the whole merged `settings_` to `.liquid/settings.liquid`, including Lake account names and URLs (`src/settings.cpp:479-480`); repository scope is the default after open (`src/app.cpp:1612`).

**Why it matters.** The user's account inventory lands in the repository; repository-shipped settings can also redefine accounts and the AI model.

**Fix.** Write only fields overridden at repository scope, never Lake accounts, and ignore accounts in repository files.

### Y-07 — A tagged release can publish ad-hoc or self-signed installers when signing secrets are missing

**Medium** · p2 · https://github.com/oramasearch/liquify/issues/77

- `.github/workflows/ci.yml:266` falls back to ad-hoc macOS signing, `:330` to a self-signed `CN=Liquify CI` Windows publisher; `release.yml:12-14,44-54` publishes what was built; the ad-hoc macOS build carries `disable-library-validation` (`packaging/macos/package.sh:257-265`). `SHA256SUMS` are published on the same channel (`release.yml:41`).

**Why it matters.** A tag push with lapsed secrets ships unsigned or self-signed installers, and the macOS one accepts any dylib (worse with Y-01). The org's no-CI rule applies: changing these workflows is Steve's decision.

**Fix.** Make the packaging script refuse to produce a release artifact on a version tag without real signing and notarisation, and decide with Steve whether the release workflow stays.

### Y-08 — Repository names and blobs used without validation or size caps; tree-sitter runs unsanitised (F14)

**Medium** · p2 · https://github.com/oramasearch/liquify/issues/78

- Names joined into paths unvalidated: `src/app.cpp:4209-4211`, `src/repository_view.cpp:144-146`.
- Blobs loaded whole with no cap or binary check: `src/editor_buffer.cpp:97,110`.
- `--print-tree` prints names raw (`src/main.cpp:67-69`, terminal escape injection); go-to-definition opens whatever path a graph result names (`src/app.cpp:3481-3490`).
- No sanitizer or fuzz coverage for tree-sitter on repository input.

**Why it matters.** A hostile repository injects terminal escapes, exhausts memory with a large blob, or reaches tree-sitter's C++ external scanner with crafted input.

**Fix.** Add a size cap with a binary-or-too-large state, validate names at the view layer, escape `--print-tree`, and run tree-sitter under ASan with upstream corpora locally.

### Y-09 — Analysis cache is read from inside the untrusted repository with reserve-from-input and unchecked enums (F15)

**Medium** · p2 · https://github.com/oramasearch/liquify/issues/79

- `reserve(*count)` from input: `src/stub_tree.cpp:126,142`; `src/interactive_analysis.cpp:665,753,761,776,786,862,970,1043`.
- Unchecked enum casts: `src/stub_tree.cpp:132`, `src/interactive_analysis.cpp:871`.

**Why it matters.** A directory that ships a crafted cache crashes the editor on open (`bad_alloc`) or feeds out-of-range enums into the analysis.

## 7. Controls that are sound

Credit where the code already does the right thing, so a fix does not undo it.

- **Identity and hardware keys (liquid).** ECDSA refuses off-curve keys and out-of-range `r`/`s`
  (`src/crypto/signature.cpp:460-487`); PKCS#1 v1.5 verification checks the exact structure
  (`:252-268`); rotation requires the new key's signature and the old key's when no compromise is
  declared (`src/identity.cpp:1058-1064`); the PIV TLV parser checks exact lengths
  (`src/identity/keys/keys.cpp:332-369`), CTAPHID reassembly is bounded (`src/identity/keys/hid.cpp:365-379`),
  TPM responses are bounded (`src/identity/custody/tpm.cpp:107-124`); Shamir refuses index 0 and
  duplicate shares (`src/identity/custody/shamir.cpp:60,176-184`); the release quorum counts distinct
  identities (`src/identity/threshold.cpp:181-205`).
- **Sealed secrets.** Canonical CBOR with exactly six fields (`src/secret/sealed_secret.cpp:357-369`),
  the header bound as associated data (`:472-476,533-538`), scope checked before decryption (`:504`),
  random 24-byte nonce (`:468`), all-zero shared secrets refused (`:456,521`), key file must be 0600
  (`src/cli/secret.cpp:250-256`).
- **DER, X.509, TUF, transparency.** The DER reader is iterative and refuses indefinite and non-minimal
  lengths (`src/asn1.cpp:85-107`); X.509 requires matching inner and outer algorithms
  (`src/x509.cpp:812-816`), refuses unknown critical extensions (`:527-531`) and requires a critical
  timeStamping EKU (`:899-904`); TUF ties key ids to the canonical key (`src/tuf.cpp:271-279`), counts
  distinct allowed keys (`:380-395`), refuses rollback and freeze (`:621-627`) and advances root by
  exactly one under both thresholds (`:666-681`); consistency and inclusion proofs follow RFC 9162 and
  tiles are verified before use (`src/lake_transparency.cpp:916-917,1047-1048,1076-1121`).
- **Network.** Servers default to loopback (`include/liquid/node_store.hpp:18`,
  `include/liquid/admission.hpp:110`, `include/liquid/workers.hpp:18,26`, `src/cli/serve.cpp:313`);
  control requests are capped at 1 MiB (`src/serve/http.cpp:125-157`); sync frames are capped at
  16 MiB with raw and compressed sizes checked (`src/sync/codec.cpp:18,506`); the HTTP client verifies
  the peer by default (`src/http1/client.hpp:24`), sets the hostname for `SSL_set1_host`
  (`src/http1/client.cpp:286`), refuses userinfo URLs (`:59`) and follows no redirects.
- **Installs and archives.** `liquid install` runs no package maintainer scripts; generated scripts use
  validated names with `shell_quote` (`src/projection/scripts.cpp:4-15`); payload paths go through
  `safe_relative` (`src/install/install.cpp:62-79`); the archive codecs parse in memory with byte and
  entry budgets (`src/formats/deflate/`, `zip`, `tar`); Git submodules become placeholders and are never
  fetched (`src/git/import.cpp:103-110`).
- **liquify.** The only process it spawns is its own binary through `SDL_CreateProcess` with an
  argument array (`src/app.cpp:1790-1807`); no `system`, `popen` or `exec*`. Plugin inputs and outputs
  are strict canonical CBOR with a depth limit of 128 and ABI version and size checks
  (`src/plugin.cpp:193-362,564-611,755-767`). AI is off by default (`include/liquify/settings.hpp:50`),
  the provider and host are fixed (`src/settings.cpp:266-272`, `include/liquify/ai_provider.hpp:47-50`),
  the key lives in the macOS Keychain or Windows Credential Manager and is never written to a file
  (`src/ai_config.cpp:20-123`), TLS verifies peer and hostname (`src/ai_provider.cpp:318-326`), the
  context is byte-budgeted and previewable, prompts are not persisted, and edits need an explicit
  Accept within the focus range (`src/assistant.cpp:135-160`). Multiplayer opens no socket of its own;
  it goes through libliquid's local API (`src/multiplayer.cpp:55-122`). There is no auto-update
  mechanism (`docs/packaging/README.md:118-119`).

## 10. Method and limits

Three reviewers read the code in parallel, each against the September document: one re-checked F1 to
F31 in liquid, one read the surfaces new since September (identity and hardware keys, sealed secrets,
DER/X.509/CMS/TUF/transparency, the HTTP servers and client, hot update and installs, the format
codecs, Git interop), one read liquify. Every Critical and High citation, and a sample of the others,
was re-read in source before filing. Submodules (Corosio, Capy, automerge-cpp, http, oramacore-cpp)
were read only where a finding depended on them (Corosio's hostname verification at `887166b`); their
own audit is the dependency item in the [pre-public checklist](pre-public-checklist.md). Nothing was
built, run or fuzzed; the line numbers will drift, so re-read each finding at the publish commit.

Both repositories have CI workflow files: liquid's `CI` is disabled; liquify's `CI` and `Release`
workflows are **enabled**. The organisation's rule is no CI, so this review neither relies on them nor
proposes changes to them; the fuzzing and sanitizer work in [L-25](#l-25) is local and on the cluster
BuildKit lane. Whether liquify's workflows stay is Steve's decision.
