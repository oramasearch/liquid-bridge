## Verdict

**The bus works.** A request answers in milliseconds, and every agent claims its task within a
second. The answers come back over pub/sub: Ask Orama in about 5 s, the Project Agent in 15–30 s,
an Auto-Suggest scan in about 50 s.

**The weak part was Ask Orama with data.** The first thing a person asks — what data do I have,
what is in it, which accounts are at risk — took 23–36 s, or never finished. Three causes stacked:

- the workspace's SQL had no `ORDER BY` or `LIMIT`;
- Ask Orama took `workspace_query`, a POST that only reads, for a change, so it never used it;
- its prompt named no data reads.

All three are fixed and deployed. The same questions now take 2–15 s and are right. The browser
pass found agents' markdown shown as raw pipes and a broken checkbox layout on Opportunities; both
are fixed and deployed.

## Findings, ranked

1. **An agent cannot tell that `workspace_query` only reads** ([lake#286](https://github.com/oramasearch/lake/issues/286), fixed).
   The OpenAPI said only POST. Every operation now carries `x-lake-action`, and Ask Orama judges by
   it.
2. **Ask Orama guessed SQL and repeated failing calls** ([agent-ask-orama#2](https://github.com/oramasearch/agent-ask-orama/issues/2), fixed).
   Prompt v2 names the data reads, `workspace_sql`'s `statement` field and the SQL subset.
3. **The workspace's SQL had no `ORDER BY` / `LIMIT`** ([zetta#912](https://github.com/oramasearch/zetta/issues/912), [zetta#1021](https://github.com/oramasearch/zetta/issues/1021)).
   Fixed by [zetta#1039](https://github.com/oramasearch/zetta/pull/1039), deployed on dev; bare
   `COUNT(*)` and multi-predicate `WHERE` remain.
4. **Agents' markdown shown as raw pipes** on `/ask` and the Factory ([lake#273](https://github.com/oramasearch/lake/issues/273), fixed).
   The first fix put the page tables' sticky header over the first row; that is fixed too.
5. **Opportunities: checkboxes floated above their words, and titles were smaller than subtitles** ([lake#274](https://github.com/oramasearch/lake/issues/274), fixed).
   Their reasons also showed backticks.
6. **Scans pile up near-duplicate Opportunities** ([lake#287](https://github.com/oramasearch/lake/issues/287), open, `decision`).
   Three options for Steve.
7. **Ask Orama names projects by id** ([agent-ask-orama#3](https://github.com/oramasearch/agent-ask-orama/issues/3), open).
8. **AgentCreator's API answer is JSON inside a string** ([agent-creator#1](https://github.com/oramasearch/agent-creator/issues/1), open).
9. **`receive_agent_events` scans the whole topic** ([lake#275](https://github.com/oramasearch/lake/issues/275), open).
   464 ms already, and growing. A TTL is not the fix: expired events move to a dead-letter topic
   that never expires.

## What is good

- **The bus.** Claims arrive within a second, nothing waits inside a request, and no body or credential
  is ever on a topic.
- **The claim contract.** It held under every attempt to break it: a person, the service token and
  the wrong agent were all refused.
- **Following a task.** The *Thinking…* page keeps working when you leave. `receive_agent_events`
  gives API and MCP callers the same live view.
- **The Project Agent** proposes and never applies. **Ask Orama** proposes changes and never makes
  them.
