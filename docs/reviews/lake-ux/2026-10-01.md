## Verdict

lake now does a great deal end to end: the four acceptance runs of #136 pass live, every page but
five is well under 100 ms, there is real in-product documentation with browser, REST and MCP paths
for each step, and Ask Orama diagnosed the worst bug of this review by itself. **But the demo path
breaks in the middle:** a newcomer following Getting started uploads a CSV fine (J3) and then cannot
train on it (J6), because Zetta's feature planner treats ordinary numeric columns as identifiers
([zetta#1216](https://github.com/oramasearch/zetta/issues/1216)); the documented recovery, *Ask the
Project Agent*, proposes the right fix but cannot apply it ([lake#438](https://github.com/oramasearch/lake/issues/438)).
And the copy-paste curl that ends the demo fails as given ([lake#439](https://github.com/oramasearch/lake/issues/439)).
Those three are the fix-first list.

## Per job

**J1 (browser).** The home page orients in one screen: *Design, train, and ship AI on your own
data*, three cards, *Getting started*. `/docs` is real documentation: five steps from a CSV to a
callable model, each with the browser path and the REST and MCP calls. 390 px has no horizontal
scroll; only the Space/Workspace selectors and breadcrumb are crushed ([lake#452](https://github.com/oramasearch/lake/issues/452)).

**J3 (browser, GIF).** Train → Data → Upload a file: 400 rows, `Loaded 400 rows into
ux_review_2026_10_01_accounts_2` with a link. The `_2` was a silent rename (the API pass had taken
the name). The Datasets table below shows a blank NAME for every row and mixes in ~20 engine tables
([lake#447](https://github.com/oramasearch/lake/issues/447)).

**J4.** The dataset page shows database, rows, bytes, columns and the first rows; it says *Format
jsonl* for a CSV and shows no column types. API: SQL cannot `count(*)` without GROUP BY or group by
a text column; an unknown column returns nulls.

**J5/J6 (browser, GIF).** New Project → Build a Pipeline ("Predict the churned column of accounts",
From data = the dataset) gives *churn skeleton*, 6 readable steps, *proposed*. Approve → Train on the
dataset, hold out 0.2 → *Check and run* → `transform_required: create_eligible_features: The feature
plan leaves no inputs this trainer can consume.` Ask the Project Agent produced a correct 28-edit
proposal in 8 s, but *Why it cannot be applied*: `compile_intent FAILED: 403 {…"credential does not
grant workspace_act"…}`. Ask Orama, asked why, answered in 180 s with the real cause: the planner
excluded `failed_payments`, `monthly_spend`, `support_tickets`, `tenure_months` as identifier-like,
leaving only `plan__one_hot`.

**J7.** Train → Runs lists every run with *Report*/*Why it failed*; study trials show as a bare
`in`. A report reads well (features, weights with "a weight is reliance, not a cause", what the run
cannot tell you) but lacks the held-out score the docs promise; Ship → Models shows it (AUC 0.708).

**J8.** Ship → Models → Publish, then the page's curl: `workspace_id is required`. With
`workspace_id` it answers from outside lake with ranked risks and drivers (5.6 s first call). API:
`expose_model` advertises an internal `/v1/models/<id>/predict` that 404s.

**J9.** Ask Orama answered a two-part question correctly and handed off to the ExperimentsAgent
with a proposal link, in 180 s. The *Talk to* list exposes internal agents. API: created agents are
not listable; *run once* stays at phase `""`; `create_agent` silently dropped an unknown `content`
key.

**J10–J12.** Organizations: "POST /v1/create_organization creates one" is the whole page. Usage: 951
B–18 KB stored, compute 0. Activity: oldest first, raw `taap:1:ed25519:…` principals. Ship →
Packages answers 502 ([lake#440](https://github.com/oramasearch/lake/issues/440)). Pages over budget:
Ask Orama 417 ms–3.9 s, Train → Agents 684 ms, Search Indexes 286 ms, Models 143 ms, Experiments
108 ms; everything else 13–81 ms ([lake#446](https://github.com/oramasearch/lake/issues/446)).

MCP: the client's tool list was stale (274 vs 352 live tools, no `workspace_id` in schemas); with
raw JSON-RPC every job behaved as on REST.

## Findings, ranked

**Blocks a customer:** zetta#1216 (feature planner), lake#438 (Project Agent apply 403), lake#439
(examples omit `workspace_id`), lake#440 (Packages 502; handler exceptions drop connections),
zetta#1217 (study trial failure hidden), lake#442 (agents unlisted, run-once stuck).

**Damages trust:** lake#441 (stale MCP tools), lake#443 (no organizations UI), lake#444 (usage),
lake#446 (page budget), lake#447 (Data page), lake#448 (docs contradict what runs).

**Rough edges:** zetta#1218 (SQL), lake#445 (activity), lake#449 (report score, trial names),
lake#450 (API naming/errors), lake#451 (Ask Orama list, long turns), orama-operator#243 (double
restart → 503s), agent-application#16 (false "rollout failed"), lake#452 (small UI items).

## What is good

- The front door and `/docs` are clear and honest, with REST and MCP next to every click.
- Most pages render in 13–81 ms of server time.
- Uploading data is one form with an exact confirmation; the dataset page shows real rows.
- Pipelines are readable (named steps, a graph), approval is explicit, and gate failures say so.
- Ask Orama is genuinely useful: it read the workspace, found the cause of a failure that the
  pipeline page could not explain, and handed off to the right agent.
- The ExperimentsAgent now proposes valid studies; Apps build and deploy with sign-in, public, and
  Postgres-bound variants; S-1 delivers decisions with a balanced holdout.
- Errors from the registry are mostly structured (`code`, `message`, `path`), and REST and MCP agree.
