# lake UX review, 2026-10-10

- **Target:** https://lake.oramadev.net (the dev AKS cluster), lake `2229b8b51509ee8fcd2d0d2ccc6a8b00c87fbf88`
  (`GET /v1/server_info`, node `prod`, store `postgres`), image `20261010p`.
- **Run by:** Claude for Steve, with `/lake-ux-review`, on 2026-10-10 (23:53 to 00:12 UTC). The
  browser half and the API/MCP half ran in parallel.
- **Surfaces:** Chrome, signed in as Steve, in a new tab at 1343 × 896 CSS px. The 390 px check was
  **not done**: the window would not shrink below 2028 px. REST `/v1` with Steve's key and a
  `User-Agent` on every call (contract `GET /v1/openapi.json`, 408 paths). MCP as raw JSON-RPC to
  `POST /mcp` (402 tools).
- **New this week, walked too:** the web app (lake#561), Drives (lake#565), Secrets and Transcripts.
- **Epic:** [lake#595](https://github.com/oramasearch/lake/issues/595). It lists 29 new issues across
  lake, zetta and agent-ask-orama, and comments on 3 existing ones. Earlier reviews:
  [lake#260](https://github.com/oramasearch/lake/issues/260),
  [lake#288](https://github.com/oramasearch/lake/issues/288),
  [lake#453](https://github.com/oramasearch/lake/issues/453).

## Verdict

**The demo path works end to end on every surface.** On 2026-10-01 training was stuck; it is not
now. A CSV goes in (400 rows in the browser, 1,500 over REST and MCP). A pipeline is built,
approved and run in 2–4 s, and its report is honest: it warns against quoting a perfect score and
says why the categorical column was left out. The model is published, and a `predict`-only key
calls it from a plain client and is refused everything else. Drives work for all three storage
kinds, including chunked uploads and a download with identical bytes. REST and MCP have full name
parity, and most errors are exemplary.

What would embarrass us in front of a customer:

- Over REST, any workspace engine error, a SQL typo included, arrives as **Cloudflare's 502 page**
  instead of lake's message ([lake#572](https://github.com/oramasearch/lake/issues/572)). This is
  the one finding that blocks a customer.
- The project page shows the description where the decision belongs
  ([lake#577](https://github.com/oramasearch/lake/issues/577)).
- Compare Runs opens on an error ([lake#576](https://github.com/oramasearch/lake/issues/576)).
- Every pipeline is named "churn skeleton" ([zetta#1238](https://github.com/oramasearch/zetta/issues/1238)).
- Ask Orama gives up on "which model scored best" and still reports `succeeded`
  ([agent-ask-orama#14](https://github.com/oramasearch/agent-ask-orama/issues/14)).

Two fixes found here are already on branches and are not deployed:

- Secrets for a person with only their own account: branch `issue-561-secrets-owner`,
  [lake#568](https://github.com/oramasearch/lake/issues/568).
- "Study" → "experiment" wording: branch `issue-561-experiments`,
  [lake#569](https://github.com/oramasearch/lake/issues/569).

## Per job

**J1 (REST, MCP; 4 calls each).** `viewer` gives the person's accounts, workspaces and ids.
`mcp_setup` gives 6 flows: pipeline, dataset, train and predict, Postgres service, volume, and
search index. There are none for Drives, Secrets or Transcripts. `list_docs` has 37 pages in 7
sections. Two problems:

- `get_doc?slug=drives` → `400 "unexpected field slug"`, although `list_docs` names each page by
  `slug`.
- `list_docs?q=upload a csv` → `[]`, while `q=upload` → 16 pages.

Thirty-five operations carry their raw id as their title. All 234 write tools are marked
`destructiveHint` ([lake#594](https://github.com/oramasearch/lake/issues/594)).

**J1 (browser).** The page sweep loaded every rail page and every workspace page through the
router. 52 of 56 loaded with no failed request. The four exceptions:

- Home's Transcripts figure shows "—" because Home asks `list_transcripts` for more than 100
  ([lake#574](https://github.com/oramasearch/lake/issues/574)).
- Deployments retries `503 store_unavailable "the platform mirror is not configured"` six or more
  times and never says the feature is not set up ([lake#575](https://github.com/oramasearch/lake/issues/575)).
- Compare Runs with no runs selected sends an empty list and errors
  ([lake#576](https://github.com/oramasearch/lake/issues/576)).
- The 503 burst after a repository drive was created (below).

**J2 (REST; 2 calls + polling).** `create_workspace` → `Pending`, then `Provisioning` ("waiting
for the workspace Zetta cluster"), then `Ready` about 40 s after the call. `environment` is a free
string, and no Docs page lists its values.

**J3 (browser).** Datasets → Load data → Upload CSV gave *"Loaded 400 rows from your CSV file into
ux_review_2026_10_10_accounts"*. The file picker is the browser's plain "Choose File", and Upload
sits mid-drawer ([lake#582](https://github.com/oramasearch/lake/issues/582)). GIFs were not
recorded in this run.

**J3 (REST, MCP; 1 call).** `workspace_act upload_dataset` loaded 1,500 rows in 1.4 s. Its errors
are good: the name is taken (with `if_exists: "rename"` suggested), the name rule is stated, and a
malformed CSV names the line. Two gaps:

- A bad `format` → `"instance not found in required enum"` ([lake#591](https://github.com/oramasearch/lake/issues/591)).
- No call turns a CSV in a drive into a dataset ([lake#593](https://github.com/oramasearch/lake/issues/593)).

**J4.** `get_dataset` and `workspace_sql` work. Over REST, every engine error is a 502 that
Cloudflare replaces with its own page. Examples: an unknown table, and `count(*) n` without `AS`.
MCP gives the real message ([lake#572](https://github.com/oramasearch/lake/issues/572)).
`DROP` is refused well. `POST workspace_sql` → 405, so long SQL must fit in a URL.

**J5.**

- Browser: the New project drawer works, but the project page's "What It Should Improve" card
  shows the Description ([lake#577](https://github.com/oramasearch/lake/issues/577)).
- REST: `compile_pipeline` → `404 "no project named …"` at `/input/project` (a top-level field)
  until `workspace_act create_project` runs. The Docs example omits that step.
- Every compiled pipeline is "churn skeleton", with fixed step names
  ([zetta#1238](https://github.com/oramasearch/zetta/issues/1238)).
- `mcp_setup` trains through `capture_intent` + `compile_intent`, while the Docs use
  `compile_pipeline` ([lake#591](https://github.com/oramasearch/lake/issues/591)).

**J6.**

- Browser: Build pipeline → Approve → Check and run → Succeeded in about 2 s. Held-out AUC was
  1.000, with *"Do not quote a perfect score"*. The categorical column `plan` was not used
  (*"categorical columns are not supported yet"*).
- The layout jumps about 90 px on Approve ([lake#578](https://github.com/oramasearch/lake/issues/578)).
- REST: `run_pipeline` before approval → `409 not_approved "… approve it (approve_plan) …"`, which
  names a `workspace_act` capability as if it were a tool. After approval the run took about 4 s:
  held-out AUC 0.890, accuracy 0.812, log loss 0.383 on 292 rows.
- The gate lists about 30 checks that do not apply, each as "pass"
  ([zetta#1240](https://github.com/oramasearch/zetta/issues/1240)).
- `run_pipeline`'s answer is 93 KB and `get_run` is 222 KB over MCP, because of the entity-key
  mapping ([zetta#1202](https://github.com/oramasearch/zetta/issues/1202), commented).

**J7.**

- Browser: the run report, lineage, outputs and log are clear. "Most at Risk" shows its evidence as
  raw JSON ([lake#581](https://github.com/oramasearch/lake/issues/581)).
- REST: `compare_runs` carries only `train.*` and `system.*` series, with no held-out score.
  `get_run_metrics` → `artifacts: []`, although its description promises a confusion matrix, ROC
  and calibration ([zetta#1239](https://github.com/oramasearch/zetta/issues/1239)).
- The GET forms of `compare_runs` and `my_permissions` cannot send arrays

  the exact `predict` call to make.
- A row missing a feature → `"score: row 0 has no 'monthly_spend'; the model needs …"`.
- A `predict`-only token from `create_token` works from a plain client and gets

- A published search index answers only internal row ids
  ([lake#596](https://github.com/oramasearch/lake/issues/596)).

- Ask Orama, MCP: a dataset question was answered correctly in 6 s.

**J10.** `create_token` is clear about scopes and expiry, and the first call is simple. A Python
`urllib` client gets Cloudflare's `403 "error code: 1010"`, and no Docs page mentions a User-Agent
([lake#589](https://github.com/oramasearch/lake/issues/589)).

**J11.**

- Secrets: for a person with only their own account it took six calls and a new workspace to
  reach the first secret ([lake#568](https://github.com/oramasearch/lake/issues/568), fixed on
  `issue-561-secrets-owner`). Once a mount exists, versions, check-and-set, list, read and metadata
  all work. `put_secret` echoes the value ([lake#590](https://github.com/oramasearch/lake/issues/590)).
- Sharing a drive folder with a person needs their TAAP id and an "attestation digest" no
  newcomer can produce, and a made-up `sha256:aaaa…` is accepted
  ([lake#585](https://github.com/oramasearch/lake/issues/585)).
- Invitations, usage (`metering_usage`) and `my_audit` work.

**J12.** Most errors are excellent:

- A missing or bad credential gets a 401 with a help link.
- Bad JSON, a wrong method, an unknown route, and a workspace that does not belong to the account
  are all reported clearly.

The weak spots:

- 502 masking ([lake#572](https://github.com/oramasearch/lake/issues/572)).
- Vague `"the request contains invalid data"` and `"conflicts with existing data"` with an empty
  path ([lake#592](https://github.com/oramasearch/lake/issues/592)).
- Kubernetes text in a schedule's status ([lake#586](https://github.com/oramasearch/lake/issues/586)).

**Drives.**

- Browser: a workspace-files drive (`hello`), a repository drive and a virtual drive. A folder, a
  shortcut, a 25 B and a 3 MiB (chunked) upload, and a download with identical bytes all worked.
- Right after the repository drive was created (23:55:12Z), four reads answered **503** in the
  browser: `workspace_status`, `list_drives`, `recent_drive_entries` and `list_repositories`.
  lake's log shows each as a single 200, and ingress logged no 503, so the 503 came from the edge.
  It did not reproduce. It is the likely cause of "creating a drive did not seem to work"
  ([lake#573](https://github.com/oramasearch/lake/issues/573)).
- REST: `create_drive` works for every kind (18 ms, 30 ms, 323 ms). The errors a form submit can
  meet are listed in [lake#592](https://github.com/oramasearch/lake/issues/592); the vague one is
  an invalid derived `repository_name`.
- The two families of drive calls differ in names and inputs, and `download_drive_file` returns no
  bytes ([lake#587](https://github.com/oramasearch/lake/issues/587)).
- A resent chunk reports incomplete, and abandoned uploads hold names
  ([lake#588](https://github.com/oramasearch/lake/issues/588)).
- Files committed through a repository drive never reach hot search
  ([lake#584](https://github.com/oramasearch/lake/issues/584)).
- The shortcut form appends to its pre-filled name ([lake#580](https://github.com/oramasearch/lake/issues/580)).

**Transcripts.**

- REST and MCP: paste (25 ms), `.vtt` upload (voices kept, timings stripped), list with `q`, get
  and update all work.
- Bad audio over REST hits the 502 masking.
- The browser shows the author as a raw user id ([lake#579](https://github.com/oramasearch/lake/issues/579)).

## What is good

- **The demo path works on every surface.** Load → train → publish → predict takes a handful of
  clicks, or about 10 calls and about 15 s of compute. `expose_model` answers the exact `predict`
  call to make. A `predict`-only key works from outside and is refused everything else.
- **The run report is honest.** It warns against quoting a perfect score, and it says which column
  was left out, why, and how to include it.
- **Drives** work for three storage kinds, including folders, shortcuts, chunked upload and a
  download with exact bytes. Virtual-drive refusals ("a virtual drive holds folders and shortcuts
  only; upload into a workspace-files drive") are a model for how errors should read.
- **REST and MCP have full name parity:** every capability is a tool with the same input.
- **The in-product Docs are thorough.** Every page gives the REST and MCP form of each step, and
