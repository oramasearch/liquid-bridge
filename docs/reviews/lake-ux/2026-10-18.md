## Per job (browser)

**J1 — Get oriented.** Home is Ask Orama, with four suggested questions, the agents and a map of
every section, each with a question to ask. Docs (sidebar) has Getting Started, Concepts and Glossary,
and a page per area. Clicking a suggestion fills the box; it does not send (fine, it can be edited).
The first suggestion's answer gives wrong directions (lake#817): "Lake Console → datasets / data
upload", "Upload dataset", "CSV or Parquet". The real path is Data → Datasets → Load data → Upload, and
it accepts CSV or JSONL.

**J3 — Load data** (GIF `lake-ux-2026-10-18-J3-J6-J8.gif`, in Steve's Downloads). Data → Datasets →
Load data → Upload → `customers.csv` (500 rows, 7 columns). Upload with the name field left as shown
→ "Please fill out this field": the grey `accounts` was a placeholder (lake#814). Named it, uploaded:
"Loaded 500 rows from your CSV file into ux_review_20261018_customers." 4 clicks, about 2 s.

**J4 — Look at the data.** The dataset page shows rows, size, columns with type and "reads as"
(boolean, identifier, numeric, categorical), first rows and partitions. Query it → SQL runs at once;
an aggregate works. A wrong column gives a good error: *column "churn" does not exist in
datasets.ux_review_20261018_customers (its columns: churned, customer_id, …)*. Every table shows
columns alphabetically, not in SELECT or file order (lake#812). The API answers the right order in
`columns`; the page builds headers from the row objects' sorted keys. The dataset page leads to no
next step toward a model, and its blue button is Keep durable (lake#818).

**J5 — Design.** Projects' empty state offers New project or "See your Opportunities". Scan my
workspace → *The scan did not finish — unauthorized: credential does not grant list_apps* (lake#795,
already filed from the e2e suite). New project: name, description, the decision it should improve →
created. Build pipeline: one sentence, "From data" picks the dataset, and methodology is "Let Lake
choose" (21 listed) → 6 steps (connect → clean → model → index → serve → act) on M-1. The names it
makes are garbled ("Predict which customers will churn the churned column") and the model's name is
79 characters (lake#816).

**J6 / J7 — Train, evaluate, approve.** Check before Approve → *approve it (workspace_act with
capability approve_plan) before verification*, which stays on screen after Approve (lake#813). Check
and run → the run page. The log is clear about what it did: label `churned`, entity `customer_id`,
features `monthly_spend, support_tickets, tenure_months`, and *not used: 'plan' … categorical columns
are not supported yet* (zetta#1203). The run took 0.46 s (18:49:32.044 → .507). The report leads with
**held-out AUC 0.823 on 121 rows**, then accuracy 0.926 against a majority-class 0.792, the feature
weights, and the most-at-risk customers with per-row reasons.

**J8 — Ship.** Ship → Models → Publish v1 → Call shows a curl. The model page has REST and MCP
endpoints, a copyable curl with the real ids, and **Try it**. Two rows scored at once (risky 0.984,
loyal 0.079). A row missing a feature gets a clear message, but numbered from zero, "row 2" (lake#819).

**J9 — Agents.** Ask Orama, "Which of my customers are most likely to churn, and how good is my churn
model?" → a ranked top 10 with drivers, plus the model's held-out AUC, accuracy, log loss and row
count, explained in one sentence. Correct against the run report. "Make a search index over my
customers dataset" → a `create_index` proposal with Confirm (nothing changed before confirming, as
claimed). Confirm → *table is required*, then "That did not work: table is required" and no way forward.
It also missed that the pipeline had already made an index over that dataset (comment on lake#794).
The agent pages (Design → Agents, Train → Agents) and MCP Connections were read, not exercised.

**J10 — Developer.** Developer → API: base URL, envelope, key creation with lifetime and access
(every operation, read-only, named capabilities), a Quick start with curl, JavaScript and Python
using the real space and workspace ids, and the Python note about the User-Agent. The JavaScript

- **The demo path works, fast, in the browser alone.** On 2026-10-01 it broke at training. Today: CSV
  → query → project → one-sentence pipeline → approve → train (0.46 s) → publish → Try it, with no
  error on the path itself.
- **Honest reports.** The run log says which columns it used and why it dropped the others. The report
  leads with a held-out score next to the majority-class baseline, and each at-risk row has its reasons.
- **Errors that teach.** A wrong SQL column lists the real ones. A predict row missing a feature names
  it and every required feature. An unauthenticated API call answers `unauthenticated` with a `help`
  link.
- **Ask Orama on the workspace's own data** gave a correct, well-made answer: the ranked table, the
  model's quality and what it means.
- **Every page has an empty state that explains itself** and a lead sentence that says what the page
  is for. No page errored.
