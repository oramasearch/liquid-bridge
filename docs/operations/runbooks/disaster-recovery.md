# Disaster recovery

What `Lake/prod` is made of, what has a backup, what does not, and how to restore each part. The
control-plane path follows the operator's `docs/lake/backups.md` (PR
https://github.com/oramasearch/orama-operator/pull/131). **As of 2026-09-05 nothing below has a
backup**: `BackupReady=False` (`control-plane backups are disabled`), no `Backup` objects, no disk
snapshots, no copy of the instance KEK. The first three steps under *Before a disaster* are the
owner's to do now.

## What the service is made of

| Part | Where | Holds | Backup today | Backup path |
|---|---|---|---|---|
| **Control database** | CNPG `lake-prod-controldb`, PVC `lake-prod-controldb-1` 50 Gi | users, credentials (hashed/encrypted), sessions, organizations, grants, repositories and their refs, forge records, **audit_events** (signed chain), metering, secrets ciphertext, PKI ciphertext, applications, `lake_identity` (wrapped seed) | **none** | CNPG Barman to Cloudflare R2 (`spec.postgres.backup`), daily base + continuous WAL |
| **Store volume** | PVC `lake-prod-store` 100 Gi, `managed-csi` | every customer's liquid store (`<customer>/store`: packs, index, collector state); the transparency log (`prod/log/`: TUF roles, tiles, checkpoints, timestamps) | **none** | Azure disk snapshots via `VolumeSnapshot` (CRDs present), scheduled; lake-level replication to a standby (lake `docs/control-plane/replication.md`) later |
| **Instance KEK** | Secret `lake-prod-instance-kek` (key `key`) | the one key that wraps the identity seed, every customer KEK, TOTP seeds, OAuth/webhook/application secrets | **none** | an offline copy in the owner's password manager or a sealed envelope; never in git, never in R2 beside the database |
| Admin bearer | Secret `lake-prod-admin` | break-glass credential | none | re-mintable: delete the Secret and the operator mints a new one (all existing admin sessions die) |
| CNPG certificates | `lake-prod-controldb-{ca,server,replication}` | internal TLS | none | regenerated by CNPG |
| Cloudflare zone token, pull secret | `cloudflare-api-token`, `oramasearch-dockerhub` | credentials | copies in `orama-system` | recreate from the providers |
| The CR | `Lake/prod` | desired state | the manifest saved at the last roll | keep `lake-prod-cr.json` from [`roll-lake-image.md`](roll-lake-image.md) in the on-call's files |

**Why the KEK matters more than the database backup.** `lake_identity` stores lake's Ed25519 seed
AES-256-GCM-wrapped by `LAKE_INSTANCE_KEK`; `keystore` stores every customer KEK wrapped the same
way; those wrap the secrets, encryption keys and PKI private keys (lake `docs/api/audit.md`,
`docs/control-plane/schema.md`). A restored database without the KEK gives a lake that cannot
sign audit events with its old identity, cannot decrypt any customer secret, and cannot verify
passkey bindings signed by the old identity. The operator mints a **new** KEK when the Secret is
absent — which quietly makes the old ciphertext unrecoverable. Treat the Secret's deletion as a
data-loss event.

**Why the database and the store must be restored to the same point.** The database knows a
repository's refs (`repository_refs`) and tombstones; the store holds the objects. A store older
than the database has refs pointing at missing objects (pull fails); a database older than the
store has unreferenced objects (collected later, harmless) and forgotten customers whose data sits
on disk. Restore the store to a point at or after the database's, then reconcile by re-pushing
from clients where refs are missing.

## Before a disaster (owner actions, in this order)

1. **Copy the KEK offline.** `kubectl get secret lake-prod-instance-kek -n lake -o
   jsonpath='{.data.key}' | base64 -d` into the owner's password manager, labelled with the date
   and `Lake/prod`. Do the same after any rotation. This is the one Secret value this document
   asks anyone to read.
2. **Turn on control-plane backups.** Create the R2 bucket `lake-prod-backups` and a bucket-scoped
   token (Object Read & Write), then the Secret and the CR fields exactly as operator
   `docs/lake/backups.md` says:
   ```sh
   kubectl create secret generic lake-prod-backups-r2 -n lake \
     --from-literal=s3ApiEndpoint='https://<ACCOUNT_ID>.r2.cloudflarestorage.com' \
     --from-literal=accessKeyId='<id>' --from-literal=secretAccessKey='<key>'
   # then in the Lake CR: spec.postgres.backup: {enabled: true, destination: {bucket: lake-prod-backups}, secretRef: {name: lake-prod-backups-r2}}
   kubectl get scheduledbackups,backups -n lake; kubectl get lake prod      # BackupReady true, Backup column populated
   ```
   Default schedule `0 0 3 * * *`, retention `30d`, path `lake-prod/controldb`, WAL gzip.
3. **Snapshot the store volume.** Create a `VolumeSnapshotClass` for `disk.csi.azure.com` if none
   exists and a `VolumeSnapshot` of `lake-prod-store`; then a CronJob (or an operator feature —
   open an operator issue under #128) that takes one daily and keeps 14. Snapshots are
   crash-consistent; liquid's store is designed for that (its packs are append-only and the
   collector is crash-safe, liquid Phase 1 #100/#126), but a snapshot taken during a push may lack
   the push's last refs — the client re-pushes.
4. **Rehearse.** Restore the database into a *new* CNPG cluster (procedure A below) and the
   snapshot into a *new* PVC (procedure B). Verify the database with `psql` against the recovered
   cluster. Verify the store by starting a throwaway `Lake` (`Lake/rehearsal`, namespace
   `lake-rehearsal`, `ingressEnabled: false`, `spec.store.existingClaim` = the restored PVC); the
   CR cannot yet adopt an existing CNPG cluster, so the rehearsal Lake gets its own empty control
   plane and only proves the store mounts and reads — an operator issue should add
   `spec.postgres.existingCluster` so one rehearsal Lake can prove both. Record the result and the
   date in [`../slos.md`](../slos.md) *Backup recency*. Once a quarter.

## Restore procedures

### A. Control database from R2

Symptoms: the CNPG cluster is unrecoverable (both pod and PVC gone, or Postgres refuses to start
with corruption) — after [`control-database-unreachable-or-full.md`](control-database-unreachable-or-full.md)
has ruled out the simple causes.

1. **Do not touch `lake-prod-controldb` or the KEK.** Scale nothing.
2. Recover into a new cluster with the manifest in operator `docs/lake/backups.md` (*Recover into
   a new CNPG Cluster*): `bootstrap.recovery.source` from `externalClusters[].barmanObjectStore`
   at `s3://lake-prod-backups/lake-prod/controldb` with the `lake-prod-backups-r2` credentials;
   optionally `recoveryTarget.targetTime` for point-in-time.
3. Wait for it: `kubectl get clusters -n lake -w`. Verify with its `-app` Secret's `uri`:
   `SELECT count(*) FROM users; SELECT max(sequence), max(occurred_at) FROM audit_events; SELECT version FROM schema_migrations ORDER BY 1;`
4. Decide: repair the original from the recovered data (CNPG `Cluster` replace), or point lake at
   the recovered cluster. The `Lake` CR names its CNPG cluster `lake-<name>-controldb` and
   injects `LAKE_CONTROL_DB_URI` from `lake-prod-controldb-app`; there is no field to point a
   `Lake` at another cluster today. The least-surprise path: **delete the broken CNPG cluster
   object only** (not the `Lake`), let the operator recreate `lake-prod-controldb` empty, then
   `pg_dump` from the recovered cluster and `pg_restore` into the new one (`kubectl exec` on the
   CNPG pods, database `lake`, owner role `lake`), then delete the recovered cluster. Confirm
   `lake-prod-instance-kek` is the **same** Secret throughout.
5. Run `GET /v1/verify_audit` → `{verified:true}`. A restored chain that verifies proves nothing was
   lost *within* the chain; compare `max(sequence)` with the last known good value to know how
   many trailing events the recovery point dropped — those actions may need to be redone by
   customers, and the loss is an incident-communication item.

### B. Store volume from a snapshot

1. Create a PVC from the `VolumeSnapshot` (`dataSource.kind: VolumeSnapshot`), same class, ≥ the
   original size, `ReadWriteOnce`.
2. Point the `Lake` at it: `spec.store.existingClaim: <restored pvc>` (the operator mounts it
   without adopting it), `kubectl apply -f` the CR; the pod rolls.
3. Verify a public repository tree and a pull; check
   `GET /v1/transparency_checkpoint` returns the current checkpoint and that
   `prod/log/checkpoints/current.json` is at or before the restored tree (an append-only log
   restored to an earlier point is *consistent*; a witnessed checkpoint newer than the restored
   tree would exist outside lake and must be reconciled by re-appending — lake
   `docs/control-plane/replication.md` describes the same rule for standbys).
4. Reconcile refs newer than the snapshot: `repository_refs` in the database may name changes the
   store lacks; clients holding those changes re-push. Communicate which repositories.

### C. KEK lost, database intact

There is no recovery of the ciphertext. What survives: the schema, users and their **password
hashes** (Argon2id, not encrypted), passkey public keys (usable, but their lake-signed bindings
verify only against the old identity, which is now unreadable), grants, repositories, refs, the
store, and the audit chain (readable and *verifiable* — verification uses the public identity
document). What is lost: lake's identity seed (a new identity must be generated; publish the
change), all customer secrets and encryption keys, PKI private keys, TOTP seeds (users re-enrol
MFA), OAuth client secrets (re-register providers), application signing seeds and webhook
secrets (applications rotate). This is why step 1 above exists.

### D. Whole cluster lost

Order: new cluster with CNPG, ingress-nginx and the operator (operator `docs/install.md`,
`docs/lake/README.md`); the namespace `lake` with the pull Secret, the zone Secret, **the KEK
Secret restored from the offline copy under the name `lake-prod-instance-kek` before the `Lake`
is applied** (else the operator mints a new one), and `lake-prod-backups-r2`; the restored store
PVC (B) ; then the `Lake` CR with `spec.store.existingClaim`; then the database (A) into the
cluster the operator created. DNS follows the new ingress address automatically. Bridge issue
#13 decides whether the new cluster is AKS again or k0s.

## Verification

After any restore, in this order: `kubectl get lake prod` Ready; `/readyz` ok; `/v1/identity`
returns the **same** `taap_id` as before (`taap:1:ed25519:FGLLRYPSZE2RQWNLJSIW4JALV23IQKOUUASJD3ITHZ5BQZTWYFRA`
on 2026-09-05); `/v1/verify_audit` true; a public repository tree renders; a signed-in user's
session works (or is re-created); a customer secret decrypts (`read_secret`).

## Who to page

lake on-call, the Azure subscription owner (snapshots, disks), the operator maintainer (CNPG
recovery through the operator's objects). Any restore that drops customer data is a customer
communication ([`../status-page.md`](../status-page.md) email template) and a legal notice check
([`../../legal/data-processing-addendum.draft.md`](../../legal/data-processing-addendum.draft.md),
breach clause).
